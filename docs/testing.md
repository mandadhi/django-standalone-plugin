# Testing and validation

## Automated (offline)

`python -m pytest` runs the whole suite offline (live tests are opt-in).

| Area | Tests |
|---|---|
| Claude manifests, inventory, commands, agents, tools, skills, rules | `test_plugin_structure.py` |
| Guard, security policy, orchestration policy vs orchestrator | `test_guard.py`, `test_security_policy.py`, `test_orchestration_policy.py` |
| Manifest hashes, adaptations, generated-adapter mapping | `test_manifest.py` |
| SDLC documentation: catalog vs framework reference, templates and owners, rule DOC-M9..M16, protocol in every agent and command, read-only agents, orchestration policy documentation section, guard compatibility (paths, read-only, no loosening), Copilot documentation parity | `test_sdlc_documentation.py` |
| SDLC registry tool on a representative Django project (`tests/fixtures/shop_project`): init and fact detection, plan (missing documents, profile, facts, not-applicable), consuming existing documents, registry vs files, stale sources and dependencies, approved-document protection and proposal flow, impact assessment, Mermaid lint, ERD vs models, embedded diagram drift, incremental update, hand-written registries | `test_sdlc_registry.py` |
| Copilot adapter: ten command skills, hidden skills/standards, agent visibility, tool mapping, `agents:` = policy specialists, skills listed per agent, links, no Claude-only syntax, no second policy, drift detection | `test_copilot_adapter.py` |

`python tools/sync_copilot_adapter.py --check` is the synchronisation validator; it fails on missing, stale or orphaned
adapter files. `--matrix` prints the parity matrix below.

## Live (Claude Code)

`python -m pytest -m live` loads the plugin through the installed CLI. Verified with Claude Code 2.1.322:
`claude plugin validate .` passes (warnings: no icon, `commands/README.md` has no frontmatter); a session lists exactly
the ten commands `django-engineering:orchestrate` and `django-engineering:django-*`, the ten agents, and no skill or
rule. Delegation to specialists and the approval gates were not re-exercised with model calls in this change.

## Live (Claude Code): SDLC documentation scenario

One real run of `django-documentation-agent` (Claude Code, `--plugin-dir`, model sonnet) against a copy of `tests/fixtures/shop_project`
with a registry holding an approved SRS (sealed), a draft API specification whose source `shop/views.py` then changed, no configuration reference
and one unregistered legacy document. Observed:

- registry read first; the stale API specification was identified and set to `stale`; it was **not** edited (owned by the API agent) and was recommended to it;
- the approved SRS was byte-identical afterwards; the missing requirement became `docs/srs.proposed.md` plus `pending_revision`, with open questions and no invented priority;
- the missing configuration reference was generated by name and purpose only (no values) and registered; unrelated documents were not generated;
- code defects found were reported, not fixed; the unregistered document was reported, not adopted blindly;
- afterwards `tools/sdlc_registry.py check` reported 0 errors (the stale and unregistered warnings the agent reported).

A first attempt failed to read the project only because the Windows 8.3 short path (`HMANDA~1`) of the test directory is rejected by Claude
Code's permission layer; the agent refused to guess and reported it. This is one run of one agent: the orchestrator's multi-agent flow, the
other specialists' documentation behaviour and Copilot were not exercised live.
