# SDLC documentation framework

The plugin treats project documentation as **shared context** for the Orchestrator and every specialist agent, from
requirements to maintenance. Agents read what exists before they work, produce what the stage needs, and update the
documents they own. The same registry, templates, rules and orchestration policy serve Claude Code and GitHub Copilot.

## The pieces

| Piece | Where | What it is |
|---|---|---|
| Catalog | `config/sdlc-documentation-catalog.json` | 7 stages, 50 document types (41 documents, 9 Mermaid diagram types) with owner agent, template, applicability profile, dependencies and change-impact rules |
| Registry | `docs/sdlc/registry.json` in **your** project | The index of the project's documents: id, name, type, stage, path, status, version, related, depends-on, sources, last updated, responsible agent |
| Protocol | `references/sdlc-documentation-registry.md`, rule `django-documentation-standards` (`DOC-M9` to `DOC-M16`) | The documentation-first behaviour every agent follows |
| Framework | `references/sdlc-documentation-framework.md` | Stage tables, owners, applicability, hand-offs, change-impact map |
| Diagrams | `references/sdlc-mermaid-diagrams.md` | Mermaid sources under `docs/diagrams/`, embedding and validation |
| Templates | `templates/` (8 new, 5 reused) | Shapes of requirements, traceability, detailed design, implementation notes, test reports, deployment and release, runbooks, maintenance records |
| Validator | `tools/sdlc_registry.py` | Optional, standard-library-only checker run by a person or CI |

There is no database, service or second orchestration engine: the registry is a JSON file, and routing is still the single
`config/orchestration-policy.yaml`.

## Stages and who writes what

| Stage | Documents | Owner agents |
|---|---|---|
| Requirements and Analysis | BRD, SRS, FRD, NFR, user stories, acceptance criteria, RTM | documentation (testing adds RTM test columns) |
| Architecture and High-Level Design | HLD, system and solution architecture, ADR, TDR, system context, C4, component diagrams | architecture |
| Detailed Design | LLD, component and integration design, sequence/activity/data-flow/workflow diagrams; database design and ERD; API specification; security design | architecture, model, api, security |
| Development | Implementation notes, module and code documentation, configuration reference, migration documentation | model, api, performance (notes); documentation; model |
| Testing and QA | Test strategy, plan, cases, execution and defect reports, performance assessment | testing, performance |
| Deployment and Release | Deployment architecture, infrastructure, CI/CD, environment configuration, release and rollback plans, deployment diagram, runbooks | documentation |
| Maintenance and Evolution | Changelog, incident reports, root cause analysis, technical debt register, architecture updates | documentation, architecture |

The **documentation agent coordinates** the registry and cross-document consistency. It is not the only writer: seven
agents own document types.

## Not every project needs everything

Applicability comes from the registry's `profile` (`minimal`, `standard`, `enterprise`), its detected `facts` (`has_models`,
`has_api`, `has_integrations`, `has_deployment`, `has_ci`) and its `not_applicable` list (type plus reason). Event-driven
documents (ADR, implementation notes, test execution and defect reports, release, rollback, incident, RCA) exist only
when the event happened. Nothing is generated just because the catalog lists it.

## Documentation-first execution

Before engineering work every agent reads the registry and opens only the relevant documents, then:

| Situation | Behaviour |
|---|---|
| Document exists and is current | Consumed and cited by id |
| Document is stale (source or upstream document changed, or the code contradicts it) | Marked `stale` and reviewed before use |
| Document is missing, applicable, and the workflow needs it | Generated by its owner from the template, then registered |
| Document is `approved` | Never edited in place; the revision is a `<name>.proposed.<ext>` file recorded as `pending_revision`; only the user's approval replaces it |
| Documents or document and code conflict | Reported with both sides and evidence, never silently resolved |
| Information is missing | Written as an assumption or asked as a question; implementation details, requirements and decisions are never invented |

Read-only agents (analyzer, reviewer) report documentation findings and never write.

## Impact assessment

Classify the changed files, update only the affected documents, and review documents that depend on them.

| Change | Documents |
|---|---|
| Models, migrations | Database design, ERD, LLD, migration documentation |
| API (serializers, views, URLs, permissions) | API specification, LLD, integration design, sequence diagrams |
| Architecture (apps, entry points) | HLD, architecture documents, C4/component diagrams, ADRs |
| Settings, dependencies | Configuration reference, deployment design, environment reference |
| Requirements | BRD, SRS, FRD, NFR, stories, acceptance criteria, RTM, then dependents |
| Tests | Test plan, test cases, execution reports |

`/django-document --impact git` does this through the documentation agent; `/django-review` and `/django-analyze` report it
read-only; `/orchestrate` reconciles it after the specialists finish.

## The ten commands

| Command | Documentation role |
|---|---|
| `/orchestrate` | Reads the registry and change set, adds a documentation context to every brief, reconciles and reports the documentation outcome |
| `/django-analyze` | Inventories documents and their consistency with the code; proposes profile and facts; writes nothing |
| `/django-design` | Consumes requirements; with `--out` writes HLD, ADRs, detailed design and diagrams |
| `/django-model` | Consumes and updates database design, ERD and migration documentation after approval |
| `/django-api` | Consumes and updates the API specification after approval |
| `/django-security` | Maintains the security design (written only with approval) |
| `/django-test` | Consumes requirements and design; updates test documents and RTM test columns |
| `/django-optimize` | Documents measured findings and decisions |
| `/django-document` | Lifecycle: registry, stage documents (`--stage`), `--check`, `--impact`, `--profile` |
| `/django-review` | Reports implementation and documentation inconsistencies; read-only |

## Validating the registry

The plugin's security guard keeps agents from running scripts stored outside the project, so agents maintain the registry by
reading and editing the JSON. A person or CI runs the validator against what they wrote:

```text
! python <plugin-root>/tools/sdlc_registry.py init --profile standard
! python <plugin-root>/tools/sdlc_registry.py plan
! python <plugin-root>/tools/sdlc_registry.py check [--strict] [--mark-stale]
! python <plugin-root>/tools/sdlc_registry.py impact --git
! python <plugin-root>/tools/sdlc_registry.py approve SRS-001 --by <name>
! python <plugin-root>/tools/sdlc_registry.py mermaid docs/diagrams/erd-orders.mmd
```

`!` runs the command in the Claude Code session so the output reaches the agents. `check` verifies schema, status against files,
references, stale sources and dependencies, approved documents changed without re-approval, unregistered documents, Mermaid structure,
embedded diagrams against their sources, and ERD entities against model classes. `approve` seals an approval with a hash so silent
edits are detectable. The Mermaid check is a structural lint, not a renderer.

## Limits

- Agent behaviour (reading the registry, respecting approvals, asking instead of inventing) is specified in their definitions and
  checked structurally by tests; it is not machine-enforced except where the guard restricts paths and tools. See [testing.md](testing.md).
- Agents cannot compute hashes or run git in all modes; staleness by agents is a reasoned decision from commit times and content, and
  the validator provides the mechanical confirmation.
- The Copilot adapter is derived from the same sources; live Copilot behaviour is not verified.
